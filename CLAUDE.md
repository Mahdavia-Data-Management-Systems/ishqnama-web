# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Ishqnama is a Quranic data web app (verses, translations, tafseer) with a monorepo structure: **frontend** (Next.js SPA), **backend** (.NET 9 API — the Minimal API on Container Apps is what the frontend calls; the Azure Functions host still builds but is no longer deployed), and **infra** (Terraform). The backend CLAUDE.md has detailed backend guidance — see `backend/CLAUDE.md`.

## Build & Run Commands

### Frontend (`frontend/`)

```bash
npm ci            # Install dependencies
npm run dev       # Dev server at http://localhost:3000
npm run build     # Static export to out/
npm run lint      # ESLint via Next.js
npm test          # Vitest unit tests (jsdom)
```

### Backend (`backend/`)

```bash
dotnet build                                    # Build solution
cd backend && docker-compose up -d              # Start PostgreSQL + Cosmos DB Emulator + the API under dotnet watch (:5081, hot reload)
cd src/Ishqnama.Functions && func start         # Run the Functions host (needs Azure Functions Core Tools) — :7071
dotnet run --project src/Ishqnama.Api           # Run the Minimal API — :5080, Scalar UI at /scalar in Development
```

### Infrastructure (`infra/environments/{dev|prod}/`)

```bash
terraform init && terraform plan    # Preview changes
terraform apply                     # Deploy
```

## Architecture

```
frontend/          Next.js 15 + React 19, static export, Azure Static Web App
backend/           .NET 9 Minimal API (+ legacy Functions host, not deployed), Clean Architecture, PostgreSQL (read-only) + Cosmos DB (user data)
infra/             Terraform modules: azure/ (swa, keyvault, log-analytics, aca-environment, aca-app, cosmosdb, app-insights)
```

### Frontend

- **Next.js 15 App Router** with `output: "export"` and `trailingSlash: true` — generates static HTML into `out/`
- **Fonts**: Google Fonts loaded via `next/font/google` (EB Garamond, Source Sans 3, Noto Serif, Noto Serif Devanagari) with CSS variable injection; local `@font-face` for Arabic/Urdu fonts. The two Nastaleeq fonts are served as `public/fonts/JameelNooriNastaleeq.v1.woff2` (5.8 MB) and its Kasheeda variant (3.9 MB), built from the 13 MB TTFs in `frontend/design/` by `npm run fonts:build` (`scripts/build-urdu-fonts.py`, needs Python with `fonttools` and `brotli`). Nastaleeq is ~25,000 ligature glyphs all reachable from Urdu text, so dropping characters saves almost nothing; the savings are WOFF2 plus rescaling the em from 2048 to 1000 units (under 0.02px of rounding at 19px, same glyphs picked). The Nastaleeq TTFs are no longer in `public/`, so `scripts/render-og-image.mjs` reads the design source. `public/staticwebapp.config.json` serves everything under `/fonts/` with a one-year `immutable` cache header, so every file there carries a version in its name (`JameelNooriNastaleeq.v1.woff2`, `PDMSSaleemQuranFont.v1.ttf`, `NafeesWebNaskh.v1.ttf`); a changed font must get the next version (`.v2`) in its filename and its `@font-face` URL in `globals.css`, or returning readers keep the old file for a year. Browsers only fetch a web font once text uses it, so the verse hooks (`use-chapter-verses.ts`, `use-juz-verses.ts`, `use-ruku-verses.ts`) start `ensureTranslationFont(lang)` from `src/lib/translation-font.ts` alongside their request and keep `loading` (the reader placeholder) until both are done, so a language switch shows the new translation once, already in its font, instead of in a fallback that shifts when the font lands. The wait is capped at 3 s (`TRANSLATION_FONT_TIMEOUT_MS`), after which the text shows in the fallback as before; a failed request is reported without waiting for the font. The helper reads the family from the translation's CSS variable (`--font-urdu`, `--font-hindi`, `--font-display`), so a font change in `globals.css` or `layout.tsx` needs no change there
- **Auth**: Azure Entra ID External (CIAM) via MSAL.js v5 client-side redirect flow with PKCE
  - Config: `src/config/auth-config.ts`
  - Components: `auth-provider.tsx`, `protected-route.tsx`, `auth-button.tsx`, `app-shell.tsx`
  - **Redirect bridge**: msal-browser v5 does not read the auth response out of the hidden iframe (silent renewal) or popup it opened; the page at the redirect URI must call `broadcastResponseToMainFrame()` from `@azure/msal-browser/redirect-bridge`, or the main frame fails after 10 s with `timed_out`. That page is `src/app/redirect/page.tsx`, its path is the `AUTH_REDIRECT_PATH` constant (`/redirect/`) in `src/lib/auth-redirect.ts`, and `redirectUri` defaults to it. `src/components/app-shell.tsx` (everything inside `<body>`) renders that route bare, with no `AuthProvider`, keep-alive ping or app chrome, so the iframe loads only the bridge. Every SPA redirect URI registered in Entra must be `<origin>/redirect/` with the trailing slash (the static export writes `redirect/index.html` and Entra matches exactly). SPA refresh tokens expire 24 h after sign-in, so this iframe path runs at least daily for a returning reader; browsers that block third-party cookies make it return `login_required`, which `MsalAuthenticationTemplate` turns into an automatic `loginRedirect` on `/library/`. On public pages (the reader) that fallback is `src/lib/session-renewal.ts`: when `acquireTokenSilent` in `src/lib/api-client.ts` throws `InteractionRequiredAuthError`, `recoverExpiredSession()` calls `acquireTokenRedirect` once per page load (a `sessionStorage` marker makes parallel fetches and the returning page share that one attempt), and if the reader comes back within 10 minutes still without a token it clears the stale account locally with `clearCache` + `setActiveAccount(null)` so the app is honestly signed out instead of redirecting on every fetch. It never signs out of Entra itself, because that would cost the reader their password prompt-free renewal. Both that redirect and `ProtectedRoute` build their request with `interactiveRequestFor()` in `src/lib/account-hints.ts`: every External ID user's username is the principal name `<guid>@MahdavisOnline.onmicrosoft.com`, which Entra prints on its sign-in page when it resolves the (already issued) opaque `login_hint` claim, so when the ID token has an email the request carries only `loginHint` with it and no `account`, because MSAL prefers the opaque claim from any account it is given (and would look up the active account if neither `account` nor `loginHint` were set). Entra looks the reader up by that email: Google and Facebook readers go straight to their provider without seeing Entra's page, and local accounts see their email instead of the GUID. The request never sets `domainHint`: in this tenant `domain_hint=google` alone fails with AADSTS90023, and with an email `login_hint` it makes Entra bounce every Google response back to Google about 20 times until AADSTS50196 (request loop), which is what a returning Google reader hit after the 24 h expiry. Tokens also carry `sid`, `emailAddress` (the mapped custom claim) and `signin_state: ["kmsi"]` when the reader chose "Stay signed in"
  - Env vars: `NEXT_PUBLIC_ENTRA_CLIENT_ID`, `NEXT_PUBLIC_ENTRA_AUTHORITY`, `NEXT_PUBLIC_ENTRA_REDIRECT_URI`, `NEXT_PUBLIC_ENTRA_API_SCOPE`, `NEXT_PUBLIC_API_URL`
  - **SPA registration settings** (all app registrations are portal-managed, not Terraform; documented in `infra/README.md` section 6): the SPA's enterprise application maps a custom claim `emailAddress` to `user.mail`, and the app registration manifest has `acceptMappedClaims: true` (without it the mapped claim is dropped) and `isFallbackPublicClient: true` (public-client PKCE flow, no client secret). Nothing in the code reads `emailAddress` yet; users are identified by `oid`
- **User data**: Authenticated users get settings persistence, bookmarks, favorites, and reading history via `src/lib/user-api.ts` → backend Cosmos DB
  - Reader settings synced via debounced save in `src/context/reader-settings-context.tsx`
  - The settings sheet (`src/components/settings-sheet.tsx`, headed "Settings") is built from **sections**, **groups** and **settings**. A section is a collapsible `SettingsSectionPanel` ("General settings", "Reader settings"), named by the `SettingsSection` union. At most one section is expanded (the sheet owns `openSection`; expanding one collapses the rest, and the open one can be collapsed too). Every section starts collapsed unless `openSettings(section)` names it (the reader toolbar's gear passes `"reader"`, the user menu passes nothing). A group is a titled `SettingsGroup` inside a section (e.g. "Show ruku marks in Quran index"), with a small muted title over its settings. A setting is a row, with its label on the start side and its control pulled to the end: a `Switch` with `styles.switchRow`, or a `styles.group` + `styles.inlineGroup` row. Rows and groups in a section are separated by a hairline
  - Bookmarks synced per-sura in `src/app/quran/[sura]/sura-reader-client.tsx`
  - Library page (`src/app/library/page.tsx`) has two sections, each with its own tabs: Bookmarks (the bookmark rail; more tabs can join it later; the whole section is left out once loaded if the reader has no bookmarks of their own, the default Nazra aside), then Lists and History below
- **Verse lists**: a signed-in reader gathers groups of ayaat into lists (a title, an optional description, and groups that each run from one ayah to another within a single sura, with an optional caption). Lists start as drafts and are published to a link anyone can open, `/lists/view/?id=<12-char id>` (the id is in the query because the static export cannot prerender user ids); a published list stays editable live, unpublishing makes the link say "This list isn't available", and deleting is permanent. The view page (`src/app/lists/view/list-view.tsx`) prints each group's Arabic alone in continuous mode through `src/components/lists/arabic-passage.tsx` (the reader's markers, sajdah underline, ruku marks from `rukuEndsInChapter()` and juz quarter marks), fetched from the Arabic-only `GET /api/chapters/{c}/arabic?from=&to=` by `src/hooks/use-arabic-verses.ts`, which shares one request per group for the visit. A group longer than `GROUP_PREVIEW_VERSES` (10) shows its first verses and **Read more**, opening the whole group in the tall `src/components/lists/sheet.tsx`. The owner sees Edit; anyone else sees Favourite (gated with `useSignInGate("favorites")`), except on a featured list, and Make a copy on every list, featured included (gated with `useSignInGate("lists")`), which asks first, then makes a draft of their own titled "Copy of <title>" (cut to the 100-character limit) with the same description and groups through `POST /api/user/lists/{id}/copy` (no credit to the original) and opens it in the editor. The editor (`src/app/lists/edit/list-editor.tsx`, behind the same settle-then-`ProtectedRoute` gate as `/library/`) saves itself 800 ms after the last change, details and groups as separate calls, one at a time, retrying on `onReady`, and reloads on window focus when nothing is waiting. Publishing asks first, saying the reader's name will show. **Add to list** on a verse in the reader (both modes, `useSignInGate("lists")`) opens `src/components/lists/add-to-list-sheet.tsx`, which appends one group on the server so an open editor keeps its work. Its range is one slider from the tapped ayah to the sura's last (no From/To boxes; left out on a sura's last ayah), whose thumb is the gold ayah marker ۝ with the chosen number inside: the native range input keeps keyboard and touch with an invisible thumb, under a drawn one placed by the browser's own `(100% - thumb) * p` formula. Above it the Arabic of the first ayah and, once stretched, the last ayah preview on one line each, never cropped: each line scrolls sideways (`useDragToScroll` for a mouse), the first opening on its beginning with its number before it, the last on its ending with its number after it; until the slider moves, a muted hint (`stretchHint`) holds the last line's place. The scroll box is LTR around an RTL `<bdi>` so the drag hook's positive `scrollLeft` holds (0 is the ayah's end). Both come from one `useArabicVerses` request for the rest of the sura. `src/context/lists-context.tsx` (`ListsProvider`, inside `BookmarksProvider` in `app-shell.tsx`) holds my list summaries and favourites. The Library page's Lists tab (`src/components/lists/saved-lists-panel.tsx`) is a vertical list in three sections, My collection, Featured and Saved (favourited lists of other readers), each list in one section only (`arrangeSavedLists()` in `src/lib/verse-lists.ts`); Featured is `FEATURED_LIST_IDS` in `src/config/featured-lists.ts`, edited in source and live with the next deploy; dev and prod keep lists in separate Cosmos accounts, as does local development (the Cosmos DB emulator from docker-compose), so it comes from `PRODUCTION_FEATURED_LISTS` on an `ishqnama.com`/`www` build (`isProductionSite()` in `src/lib/page-metadata.ts`, the same check robots.txt uses), `LOCAL_FEATURED_LISTS` on `localhost`/`127.0.0.1` and `DEV_FEATURED_LISTS` on any other, all from `NEXT_PUBLIC_SITE_URL` at build time. An entry marked `byAdmin: true` is credited to the site: `listOwnerName()` in `src/lib/verse-lists.ts` shows "Admin" in place of the owner's name on the list page and the Library row (display only; the API still returns `ownerName`). Featured lists are read through the anonymous batch `GET /api/lists?ids=`. A favourite whose list was unpublished or deleted shows "No longer available" with Remove. Favourites are generic (`kind`), so chapters, rukus and verse ranges can be added later. Copy lives in `src/config/lists-copy.ts` under the readiness-copy rules (`src/config/__tests__/lists-copy.test.ts`). `/lists/` is disallowed in robots.txt and is not in the sitemap: lists are readers' own content. Design in `plans/verse-lists-spec.md`
- **API keep-alive and readiness**: `src/components/api-keep-alive.tsx` (mounted in `src/components/app-shell.tsx`, skipped on the redirect bridge route) pings `GET /api/healthz` on load, on tab visibility, on the browser `online` event and every 2 minutes while the tab is visible, pausing when hidden, so the scale-to-zero Container App stays warm while someone is reading. The ping is also the probe behind `src/lib/api-readiness.ts`, a module-level store exposing `unknown | warming | ready | unreachable` through `useApiReadiness()`: `warming` after the ping has hung for 3 s (cold starts take ~50 s on dev, so the ping timeout is 90 s), `ready` when it answers (which runs every `onReady()` callback once), `unreachable` on failure, timeout or offline (then it re-pings every 15 s, and `requestProbe()` pings on demand). `/api/healthz` is the only route safe to ping: it is anonymous, skips the database, and is excluded from the long-lived `Cache-Control` header every other `/api` route carries
- **Cold-start UI**: while the store says `warming` or `unreachable`, the loading rail breathes instead of gleaming, `src/components/api-warmup-notice.tsx` hangs a gold bookmark ribbon from the app bar (the only looping motion is the rail; both follow the bar's real bottom edge via `useAppBarBottom()` in `src/lib/app-bar-offset.ts` and clamp at the viewport top, because the sticky bar scrolls away with the `height: 100%` body on long pages), the reader placeholder and the bookmark shelves (skeletons from `src/components/bookmark-tile-skeleton.tsx`) explain the wait, the settings sheet shows a sync line, and the create-bookmark dialog shows a helper line (its POST has a 90 s abort). `src/context/reader-settings-context.tsx` never treats a failed settings GET as loaded (it retries on `ready`), keeps changes made before the GET succeeded in a pending patch merged over the server values, and queues PUTs while warming, flushing the latest value once on `ready`. `src/context/bookmarks-context.tsx` exposes `status` and refetches a failed GET on `ready`. All copy lives in `src/config/readiness-copy.ts` and must avoid technical words (no "service", "API", "server"); the audience includes readers unfamiliar with technology. Design in `plans/frontend-cold-start-handling-spec.md`
- **Real-user monitoring**: `src/components/telemetry.tsx` (mounted in `app-shell.tsx` outside `AuthProvider`, so it is skipped on the redirect bridge) drives `src/lib/telemetry.ts`, a facade over the Application Insights browser SDK. The SDK (~72 KB gzipped) is imported dynamically after the window `load` event and an idle moment, so it is never in any page's first-load JS. Calls made before it loads are buffered (50 at most). Without `NEXT_PUBLIC_APPINSIGHTS_CONNECTION_STRING` (an SWA app setting from Terraform, read by `deploy-frontend.yml`) every call is a no-op, which is the case for local dev and tests. It records a page view per route with a fresh operation ID, Core Web Vitals labelled with the landing route (`routePattern()` turns number-only segments into `[n]`; the Web Vitals callback is module-level because `useReportWebVitals` re-reports when its callback changes), JS errors, and cold-start waits via `src/lib/api-warmup-telemetry.ts` (`api-warmup-ms` and `api-unreachable`, observing `subscribeApiReadiness`). Fetch tracking keeps only calls to the API origin (`isApiCall`): Next.js prefetches every visible link's `?_rsc=` payload, hundreds on the Quran index, and those would use up the daily cap. The SDK's own correlation header is off (`enableCorsCorrelation: false`). Instead `api-client.ts` adds `traceparentHeader()` only to requests that already carry `Authorization`, because a `traceparent` on an anonymous GET would make it a preflighted CORS request. Signed-in readers are identified by `hashUserId(oid)` (first 16 hex characters of SHA-256, the same as the API's `UserHash`), set from the MSAL `ACTIVE_ACCOUNT_CHANGED` event in `auth-provider.tsx`. Reader activity events are the `TelemetryEvent` union in `src/lib/telemetry-events.ts`. `trackEvent` drops any property key outside `TELEMETRY_PROPERTY_KEYS`, so a property may hold a choice or a count but never free text (no search text, verse text, names or emails). To add an event, add one name there and one `trackEvent` call at its site. The privacy page's "How the site is used" section describes all of this; keep it in step. Design in `plans/app-insights-observability-spec.md`
- **Global loading indicator**: `src/components/global-loading-indicator.tsx` (mounted in `src/components/app-shell.tsx`, outside `AuthProvider` so it works before MSAL initialises) lights up a 2px gold rail on the seam between the app bar and the page while API requests are in flight. Every network call in `src/lib/api-client.ts` is counted via `beginRequest()` from `src/lib/pending-requests.ts`, from before `fetch` until the body is parsed, including the keep-alive ping; MSAL token acquisition is not counted. To avoid flicker it paints nothing until requests have been pending for 300 ms, then stays at least 600 ms, lingers 150 ms after the last request settles (bridging the reader's chained verse-page calls) and fades on opacity only. It is `position: fixed`, `pointer-events: none` and `aria-hidden`; the per-page inline loaders remain the explanatory loading state
- **Dark mode**: readers choose Light (the default), Dark or Match my device from the appearance button in the app bar (`src/components/navigation/theme-menu.tsx`), open to everyone and never behind the sign-in prompt. The choice is kept per browser in `localStorage` (`ishqnama-theme`: `light`, `dark` or `system`), not in the account settings; with nothing stored, or storage blocked, the page is light whatever the device prefers (`DEFAULT_THEME_PREFERENCE` in `src/lib/theme-script.ts`). `themeScript()` in `src/lib/theme-script.ts` (hook-free, so the server root layout can import it) is inlined in the layout's head and sets `data-theme`, `color-scheme` and the `theme-color` meta on `<html>` before first paint, so the static pages never flash, including `/redirect/`; `<html>` carries `suppressHydrationWarning` for that. The store in `src/lib/theme.ts` (`useTheme()`) then follows the device while on Match my device, follows other tabs through the `storage` event, and keeps a choice for the visit when storage is blocked. The palette is a token swap: `globals.css` keeps the light values in `:root` and redefines them under `@media screen { :root[data-theme="dark"] }` (screen only, so printing stays light). Teal is split into a text role (`--teal-primary`, lightened in dark) and a fill role behind white text (`--fill-primary*`, used by the primary button, active segment and switch), and error likewise (`--color-error` for text, `--fill-danger*` for the confirm dialog's button). Hover backgrounds and hairlines use the `--tint-teal-N` / `--tint-ink-N` scale (N is the alpha in hundredths). Every colour in a CSS module or inline style must be a token: `src/app/__tests__/no-hardcoded-colours.test.ts` fails on raw colours except white, black and gold tints, and `theme-tokens.test.ts` fails when a light colour token has no dark value. The teal logo goes through `src/components/themed-logo.tsx`, which renders the teal and gold marks and lets CSS show the one for the theme. The manifest, favicon and OG image stay light. Design in `plans/frontend-dark-mode-spec.md`
- **PWA name per environment**: `public/manifest.json` names the app "Ishqnama". An inline head script from `src/lib/pwa-manifest.ts` (rendered in the root layout) suffixes the environment for installs from `<sub>.ishqnama.com` hosts other than `www`, e.g. "Ishqnama - Dev" on dev.ishqnama.com, by swapping the manifest link for a data: URL copy with the new name and setting `apple-mobile-web-app-title`. It has to be runtime, not a build-time env var, because the same derivation has to leave the prod build's `ishqnama.com` and `www` hosts untouched while naming every other environment host. Production and unknown hosts keep the static manifest untouched
- **The printed volume**: `src/components/book-model/book-model.tsx` renders the Noor e Imaan book as a Three.js scene on the signed-out home hero (`variant="hero"`, pointer tilt), the continue-reading card (`variant="card"`, a gold ribbon at the reader's `quranProgress()` through all 6236 verses, from `src/lib/quran-progress.ts`) and the About page (`variant="inspect"`, drag to rotate, pinch to zoom; a plain mouse wheel still scrolls the page, only a trackpad pinch, which arrives as a ctrl+wheel event, zooms). The component owns lifecycle only: it shows the poster `public/images/noor-e-imaan-book-poster.webp` first, and only when `canRenderBook()` in `src/lib/book-model-support.ts` passes (no reduced motion, no Save-Data, at least 2 GB device memory, WebGL 2 available), the box is within 200 px of the viewport and the window has loaded does it `import()` `book-scene.ts`, so Three.js is a separate chunk never loaded by `/quran/*`. The scene renders on demand (no frames at rest) and any failure leaves the poster. The consumer sizes the box through `className`; the component's own default size sits in a `:where()` rule so it never outranks the consumer's class. The served model `public/models/noor-e-imaan-book.v1.glb` (about 370 KB, budget 500 KB) is built from the 34 MB Blender export `design/noor_e_iman_book.glb` by `npm run model:build`; the poster is captured from the live dev server by `npm run model:poster` (needs local Chrome; the dev server must not share its `.next` folder with a concurrent `npm run build`, which 404s the dev chunks). The cover is a single mesh with no hinge, so the book does not open; the spec `plans/frontend-book-model-spec.md` records the Blender work an opening transition would need. Copy rules from the cold-start work apply: nothing says "3D", "model" or "loading"
- **Sharing a verse**: the Share button on a verse (continuous-mode block or verse-mode popup) opens `src/components/scripture/share-verse-sheet.tsx`, a bottom sheet headed simply "Share" over the verse reference, with two options named for what the recipient receives rather than where the link opens from: **"This ayah"** shares the chapter link (`/quran/<c>/?verse=<v>`, which scrolls to and flashes the verse; hint "<chapter name>, verse <v>") and **"This ruku"** shares the ruku within the juz (`/quran/juz/<j>/ruku/<r>/`, deliberately without a `?verse=` query: the ruku link shares the passage and opens at its start; hint "Ruku <r> of juz <j>"). A third "From its juz" option (`/quran/juz/<j>/?verse=<c>-<v>`) was removed as redundant with the ruku one, and the options were renamed from "From its chapter"/"From its ruku" at the same time. The juz and ruku numbers come from the verse's `RukuDto` in the static `RUKU_BY_ID` map (`src/data/rukus.ts`), so they are available immediately; the ruku option falls back to disabled with the hint "Finding its place in the book" only if a verse's ruku is missing. Link and message builders live in `src/lib/share-verse.ts`; the message opens with "Noor-e-Imaan | <chapter name> <c>:<v>", plus " | Juz <j>, Ruku <r>" when shared from the ruku (so the recipient still sees which verse prompted the share even though that link opens at the ruku's start), then the translation as displayed on its own line, never the Arabic. The link travels separately: `navigator.share` gets it in `url` only (share targets append `url` to `text` themselves, so putting it in both printed it twice), and the clipboard fallback appends it once to the copied text, with a "Copied" confirmation in the sheet that closes it after a moment
- **Link previews**: every page carries a title, description and Open Graph / Twitter card built by `pageMetadata()` in `src/lib/page-metadata.ts` (reader routes use `suraMetadata`, `suraRukuMetadata`, `juzMetadata` and `juzRukuMetadata` in `generateMetadata`; client-component pages get theirs from a server `layout.tsx`: `/quran/`, `/library/`, `/search/`). Always go through the helper, because Next.js replaces rather than merges a parent's `openGraph`, so a page setting only `openGraph.title` would lose the image. Crawlers run no JavaScript and need absolute URLs, so the root layout's `metadataBase` comes from `NEXT_PUBLIC_SITE_URL` (an SWA app setting in `infra/environments/*/ishqnama-web.tf`, read by `deploy-frontend.yml`; falls back to `https://ishqnama.com`). The single shared image `public/images/og-ishqnama.jpg` (1200×630, under WhatsApp's ~300 KB limit, content centred for its square crop) is rendered by `npm run og:image` (`scripts/render-og-image.mjs`, needs local Chrome) from the gold logo, book poster, MDMS mark and Nastaleeq font. `design/ishqnama-web-social-preview.png` is the GitHub repository's social preview for developers and must not be used on the site, since it shows the repo link
- **robots.txt**: generated at build time by `src/app/robots.ts` (`dynamic = "force-static"`, required under `output: "export"`) from `robotsFor()` in `src/lib/robots.ts`. Only a build whose `NEXT_PUBLIC_SITE_URL` host is `ishqnama.com` or `www.ishqnama.com` lets crawlers in, apart from `/redirect/`, `/library/`, `/search/`, `/lists/` and `/articles/`, and shuts the AI crawlers named in `AI_CRAWLERS` (training, AI search and assistant fetchers, plus the `Google-Extended` and `Applebot-Extended` opt-out tokens) out of the whole site in a group of their own. Search engines and link-preview fetchers must never go on that list, or Google results and WhatsApp previews break; the robots test checks this. robots.txt is a request, not enforcement: scrapers that ignore it would need Cloudflare proxying with its AI-bot blocking, which the site does not use (its records are DNS-only); every other build (dev.ishqnama.com, and local builds, since `.env.local` sets `http://localhost:3000`) disallows everything. Only the production rules carry the `Sitemap:` line
- **sitemap.xml**: generated the same way by `src/app/sitemap.ts` from `sitemapFor()` in `src/lib/sitemap.ts`, with absolute URLs on the `NEXT_PUBLIC_SITE_URL` origin: the public static pages, the 114 chapters, the 30 ajza and the chapter ruku pages (670 URLs). Two kinds of page are left out so search engines are not offered the same text under two URLs: the juz ruku pages, which repeat a chapter ruku, and the ruku page of a single-ruku chapter, which repeats the chapter. A new public page needs its path added to `STATIC_PATHS` there. `src/lib/__tests__/sitemap.test.ts` checks the sitemap never lists a path that robots.txt disallows
- **Public pages**: `/`, `/about`, `/contact`, `/terms`, `/privacy`, `/redirect/` (MSAL bridge), `/lists/view/` (published verse lists), `/articles/` (titles only; the essays' text needs an account), `/nooreimaan/dua/` (the dua for completing the Quran from the end of Noor e Imaan, text in `src/data/khatm-dua.ts`, taken from the book's `p.doa` paragraph) and all of `/quran/*`. The reader is open to anonymous users; verse explanations (tafseer) are the paid-for feature: the API strips `explanation` from every verse response unless the request carries a valid bearer token (`StripExplanations` in `backend/src/Ishqnama.Api/Helpers/AuthExtensions.cs`), and the frontend sends one when it has an account via `apiFetchWithOptionalAuth`
- **Articles**: `/articles/` is the index of the Noor e Imaan essays, built from the public titles in `src/data/articles/nooreimaan.json`, and `/articles/nooreimaan/<slug>/` is one essay. The essay text is never in the static bundle: it comes only from `GET /api/articles/nooreimaan/{slug}` (signed-in, `Cache-Control: private, no-cache` with a per-essay content ETag, so a corrected essay reaches readers who have it cached) through `useEssay` (`src/hooks/use-essay.ts`) inside `EssayGate` (`src/components/articles/essay-gate.tsx`, which settles auth, then shows the sign-in prompt for anonymous readers or the cold-start placeholder while the text loads). `EssayBody` renders the book's two-column tables as facing quotations, the Arabic and its translation side by side. Both pages carry a Share button (`src/components/articles/article-share-button.tsx`, open to everyone): it shares the page's own link through `shareVerse()` (system share sheet, else clipboard), with the essay's Urdu and English titles as the message, never its text, and records `article-shared`. The converter `scripts/build_nooreimaan_articles.py` (`npm run articles:build`; `npm run articles:test` runs its tests) writes the embedded JSON in `backend/src/Ishqnama.Application/Articles/NoorEImaan/` from the gitignored `.ishqnama/articles/31.html`. `/articles/nooreimaan/` redirects to `/articles/` in `public/staticwebapp.config.json`. `/articles/` is disallowed in robots.txt and not in the sitemap. Design in `plans/frontend-articles-spec.md`
- **Sign-in prompt**: account-only controls are shown to every reader; never hide one or let its click do nothing. `src/context/sign-in-prompt-context.tsx` (`SignInPromptProvider`, mounted in `app-shell.tsx` inside `AuthProvider`) renders the one `src/components/sign-in-prompt-sheet.tsx` and exposes `useSignInGate(feature)`, which returns `gate(action)`: signed in it runs the action, anonymous it opens the sheet for that feature. `useSignInPrompt()` gives `promptSignIn`, `dismiss` and `authSettled` (`inProgress === None`) for pages that prompt on arrival; those must wait for `authSettled` or a returning reader sees the prompt flash mid-redirect. Copy lives in `src/config/sign-in-copy.ts` (`SignInFeature` union plus title and body per feature) under the same non-technical rule as the readiness copy, enforced by `src/config/__tests__/sign-in-copy.test.ts`. Sign-in is the existing `loginRedirect`; nothing is replayed after it. Gated today: the reader-toolbar settings gear, the bookmark and Add to list buttons on a verse, Favourite on a shared list, the list editor, the essays (`EssayGate`, feature `articles`), `/library/` (via `src/components/library-gate.tsx`, which shows the spinner until auth settles, then the page shell with the prompt for anonymous readers, and `ProtectedRoute` only for signed-in ones) and search (an anonymous keystroke is swallowed and opens the prompt instead). To add a feature: one entry in the copy file, one `useSignInGate` call at the site. Design in `plans/frontend-sign-in-prompt-spec.md`
- **Protected pages**: `/library` shows "Library" in the navigation to everyone; anonymous readers get the page shell with the sign-in prompt (see **Sign-in prompt**), signed-in readers go through `<ProtectedRoute>` inside `src/components/library-gate.tsx`. `/search` is public UI; an anonymous keystroke in the search field is swallowed and opens the sign-in prompt instead, and the `/api/search` call requires a token
- **Ruku data**: all 556 rukus (`RukuDto` rows) are static data in `src/data/rukus.ts`, a snapshot of `GET /api/rukus`, since the Quran's ruku divisions never change. The frontend never calls that endpoint: the reader looks up a verse's ruku with `RUKU_BY_ID`, the ruku reader resolves its `rukuId` with `rukusInChapter()`/`rukusInJuz()` before its one `GET /api/rukus/{id}/verses` call, and `generateStaticParams` uses the derived `RUKU_COUNTS_BY_SURA` and `RUKU_RANGES_BY_JUZ`. `src/data/__tests__/rukus.test.ts` checks the snapshot against the chapter verse counts. Likewise the 30 ajza (`JuzDto` rows) are a snapshot of `GET /api/juz` in `src/data/juz.ts` (`JUZ`, `JUZ_BY_NUMBER`), used by the Quran index's Juz view and the juz reader's header; the frontend never calls `/api/juz`
- **Juz quarter marks**: the quarter, half and three-quarter points of each juz are static data in `src/data/juz-quarters.ts` (`JUZ_QUARTERS`, 90 rows), taken from the `HizbQaurter` table in Tanzil's `quran-data.js` (the 3rd, 5th and 7th hizb quarter of each juz; Madani placement, so a few points may differ from an Indo-Pak mushaf). Each row is the first verse of the new quarter, but the mark hangs on the verse before it (`JUZ_QUARTER_BY_VERSE`, keyed `"c-v"`), at the boundary where the ruku ع also sits, so when a quarter opens a chapter the mark ends the previous chapter. `src/components/scripture/juz-quarter-mark.tsx` prints الربع / النصف / الثلاثة in gold as the last child of `AyahMarkerContainer`, stacked under any sajdah or ruku mark, in both reading modes. `src/data/__tests__/juz-quarters.test.ts` checks every point falls inside its juz in `src/data/juz.ts`
- **Index ruku rails**: each card in the Quran index (`src/components/scripture/quran-index.tsx`, on `/quran/` and the home page) is a header link to the chapter or juz plus, below it, `src/components/scripture/ruku-rail.tsx`: a horizontal rail with one link per ruku, each drawn as the reader's full `RukuMark` (chapter rank, verse count, juz rank). Whether a rail shows follows two reader settings in the settings sheet's "General settings" group, "Show ruku marks in Quran index": **For sura** (`showSuraRukuMarks`, off by default) and **For juz** (`showJuzRukuMarks`, on by default). Anonymous readers get the defaults, and signed-in readers' choices are saved with their other settings (the backend `UserSettingsDto` gives both parameters the same defaults, so a save from an older client leaves them as they were). When shown, a chapter's rail needs more than one ruku; a juz always has one. A hairline marks where the rail crosses a boundary (`breakAt`): a new juz in a chapter rail, numbered under the line, and a new chapter in a juz rail, numbered over it. The hairline and its number are drawn in the rail's gap, so the marks either side stay evenly spaced. Juz quarter points show as small muted ¼ / ½ / ¾ at the foot of the rail, absolutely positioned so no tile moves: under a ruku whose middle holds the quarter's mark verse, or in the gap after a ruku that ends on it (`JUZ_QUARTER_BY_RUKU` in `src/data/juz-quarters.ts`, built from the same mark verses as the reader's `JUZ_QUARTER_BY_VERSE`); the glyph is `aria-hidden` and the ruku link's name carries the quarter instead. The numbers follow `useReaderSettings().lang`, which is Urdu for anonymous readers and the saved setting once signed in. The card is a `div`, not a link, because the rail's links cannot nest inside one. The rail uses `useDragToScroll` but deliberately not `useWheelToHorizontal`, so the wheel still scrolls the page past the stacked rails. The index's Sura/Juz choice is remembered per browser in `localStorage` (`src/lib/quran-index-view.ts`, key `quran-index-view`), not in the account settings; the prerendered page shows Sura and switches to the saved choice after mount. In tests, Node 25's own experimental `localStorage` global shadows jsdom's and has no methods, so tests stub an in-memory one with `vi.stubGlobal`
- **SPA routing**: `public/staticwebapp.config.json` configures Azure SWA fallback to `index.html`
- **Path aliases**: `@/*` maps to `src/*`

### Backend

Clean Architecture: Domain → Application → Infrastructure → presentation (`Ishqnama.Functions` and `Ishqnama.Api`, same `/api` routes). Two data stores:
1. **PostgreSQL** (read-only) — Quran data served via `IQuranReadOnlyRepository` with `CachedQuranReadOnlyRepository` (loads all data into memory on first request)
2. **Cosmos DB** (read-write) — User data (settings, bookmarks, favorites, history) via `IUserDataRepository` in the `user-data` container, protected by JWT auth middleware, and verse lists via `IVerseListRepository` in the `lists` container (partitioned by `/id`, so a published list's link is a point read by anyone)
3. **Search** — `/api/search` searches translation/tafseer text, protected by JWT auth to prevent abuse

See `backend/CLAUDE.md` for full details.

### Infrastructure

Terraform modules deploy to Azure: Static Web App (frontend), Container Apps (API with a PostgreSQL sidecar, scale-to-zero), Key Vault (secrets), Cosmos DB (user data, free tier), Log Analytics (`modules/azure/log-analytics`, one workspace per environment, `ishqnama-<env>-logs`, used by both the Container Apps environment and Application Insights), Application Insights (`modules/azure/app-insights`, workspace-based). The free 5 GB a month of Log Analytics ingestion is per billing account and shared by dev and prod, so each environment caps its workspace (`daily_quota_gb`: dev 0.05, prod 0.1) and its Application Insights resource (`daily_data_cap_in_gb`: dev 0.04, prod 0.08). The Application Insights connection string ships in the public JS bundle, so these caps are what keep injected telemetry at $0. The SWA's `NEXT_PUBLIC_API_URL` is `https://api.dev.ishqnama.com/api`, from `local.api_url` in `infra/environments/dev/ishqnama-api.tf`. That custom domain (Cloudflare DNS-only CNAME to the Container App FQDN, `asuid` TXT record, and Azure managed certificate) was added by hand in the portal and is not in Terraform. Container Apps has no path routing: the hostname selects the app and the path passes through, so the `/api` prefix is simply the `MapGroup("/api")` in the API's `Program.cs`. Two environments: dev and prod. `infra/environments/prod/` mirrors dev with prod names (`rg-ishqnama-prod`, `ca-ishqnama-api-prod`, `cosmos-ishqnama-prod`), `ishqnama.com`/`www.ishqnama.com` as the frontend hosts (the former `preview.ishqnama.com` UAT host has been retired: its DNS record and Entra redirect URI are gone) and `https://api.ishqnama.com` as the API URL, reads the CIAM tenant from the `core-prod` Terraform Cloud workspace (`mdms_core_workspace` variable) and defaults `api_image_tag` and `db_image_tag` to `latest`. Dev and prod each have a dedicated Azure subscription, so each gets its own Cosmos DB free-tier account. Azure auth via OIDC federated identity. Everything Terraform does not manage (subscription and resource provider setup, the CI service principal and its Contributor role, GitHub environment variables, Terraform Cloud workspaces, custom domains, and every Entra app registration) is documented step by step in `infra/README.md`. All Entra app registrations (SPA, `Ishqnama API`, the CI service principal) are managed by hand in the portal; Terraform only consumes their client IDs, so never propose `azuread` resources for them.

## CI/CD

GitHub Actions workflows in `.github/workflows/`:
- **`ci.yml`** — Main pipeline: build backend (+ push API image) → deploy infra → deploy frontend (dev). The image version from `build-backend.yml` is passed to `deploy-infra.yml` as `api_image_tag`, so every push changes the Container App's image reference and Terraform rolls a new revision (re-pushing a fixed tag would not). A `changes` job (`dorny/paths-filter`) gates the deploy jobs by changed paths: `setup-zone` runs for `infra/environments/cloudflare/`, `infra-dev` for `infra/` or `backend/` (Terraform rolling the image tag is what deploys the API), and `deploy-frontend-dev` for `frontend/` or whenever `infra-dev` ran (the frontend bakes SWA app settings into its build). Each filter also includes the reusable workflow it drives. `build` runs only for `backend/` changes; when it is skipped but `infra-dev` still runs, an `api-version` job resolves the newest `api-v*` git tag so the Container App keeps its current image reference. A manual `workflow_dispatch` run builds and deploys everything
- **`build-backend.yml`** / **`deploy-frontend.yml`** / **`deploy-infra.yml`** — Reusable callable workflows. `build-backend.yml` runs two parallel jobs: a Release build of the backend solution, and build + push of the `noormahdi/ishqnama-api` Docker image. For non-prod environments the image is tagged with a patch-bumped semantic version from `api-v*.*.*` git tags plus `:<environment>`, the git tag is created (callers need `contents: write`), and the version is exposed as the `api_image_version` output. Its `prod` branch (push `:latest` only, no version or git tag) is no longer used: prod images are promoted from dev versions by `prod-release.yml`. The Functions host in `backend/src/Ishqnama.Functions` is built as part of the solution but has no deployment target any more
- **`prod-release.yml`** — Manual trigger for production deployment. It promotes rather than rebuilds: a `resolve-api-version` job takes an optional `api_image_version` input (defaulting to the newest `api-v*` git tag), checks the tag and the Docker Hub image exist, retags that image as `:latest` without rebuilding, and passes the version to `deploy-infra.yml` as `api_image_tag` so the prod Container App rolls to exactly the image that ran in dev. The frontend deploy follows, as in dev. A `concurrency` group serialises releases
- **`destroy-infra.yml`** — Manual trigger to tear down infrastructure
- **`pr-validation.yml`** — Runs on `pull_request` into `main`: frontend build, backend Release build, `terraform fmt -check`. It is the only workflow a fork can trigger, so it holds no secrets, declares no environment and takes a read-only token; its three job names are required status checks on `main`

Push to `main` triggers the full dev deployment pipeline.

The repository is public, so deployments are fenced off with GitHub settings rather than code: the `dev`, `prod` and `cloudflare` environments accept deployments from `main` only (which, given the `...:environment:<env>` federated credential subject, is what binds Azure access to `main`), `prod` requires a review, workflows may only use actions on an allowlist, and `api-v*` tags are protected from deletion and force-moves. All of it is documented in `infra/README.md` under **Repository protection**.
